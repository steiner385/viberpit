# Vetted Engineering Frameworks

Status: Proposed. This document proposes policy and implementation; it does not approve packages or enable enforcement.

## 1. Goal and non-goals

Standardize vetted engineering guidance across projects managed by ViberPit, starting with Impeccable for UI/UX. Make the selected guidance discoverable to agents, connect its outputs to SDLC decisions, and demonstrate that it improves results before making it mandatory. Framework adoption is a versioned engineering change with evidence, an owner, and rollback.

ViberPit owns policy, applicability, evidence validation, and enforcement. Third-party frameworks supply selected domain guidance. Installing a skill, invoking it, or receiving an agent's completion claim is not proof of quality.

Extend existing sources of truth:

- `.agents/contract.json` and `.agents/agentctl.py` own portable instructions and skill projections. The current contract already identifies Impeccable as `provider_built`; its distinct provider builds must remain intentional, traceable projections.
- `server/sdlc/gates.py` owns named lifecycle gates and risk-based automatic resolution. Integrate framework evidence into the existing stage decisions; do not create a parallel lifecycle engine.
- `server/sdlc/prompts.py` already accepts organization skill constraints for specifications. Extend stage context to carry the resolved framework selection and evidence obligations.
- `server/sdlc/evals.py` and `scripts/run_evals.py` own eval aggregation and the static corpus. Currently `--kind agent` lists cases; it does not execute live agent evaluations. Live evaluation execution is work in this proposal.
- `server/library/` supplies inventory and editing surfaces, not proof that installed material is vetted.

Non-goals: bulk-installing marketplaces, replacing repository constitutions, forcing every framework into every task, introducing a second process framework, permitting plugins to approve releases, or treating aesthetic scores as objective merge criteria. This proposal does not change native agent binaries or assume upstream installation instructions prove compatibility with ViberPit's installed engines.

## 2. Vetting checklist for third-party skills

Vet each selected skill and its complete dependency closure, rather than approving a repository by reputation. Record the following in a reviewable admission report:

- **Identity and provenance:** upstream repository, immutable commit SHA, release if present, selected paths, content hashes, license and attribution obligations, maintainer activity, and relevant security history. Floating branches and unpinned downloads cannot identify an approved installation.
- **Instruction review:** read descriptions, frontmatter, prompts, nested references, generated provider builds, and agent definitions. Check for instruction injection, unsolicited network requests, credential access, permission escalation, destructive defaults, conflicting review rules, and claims of authority over ViberPit policy.
- **Executable tooling and hooks:** enumerate installers, scripts, binaries, native hooks, MCP dependencies, background processes, telemetry, update mechanisms, and transitive downloads. Impeccable now ships executable tooling and hooks, so skill text alone is insufficient to vet it. Pin executable artifacts and verify their hashes separately; reject installation-time or first-run downloads that escape the approved dependency set.
- **Dependency completeness:** verify referenced files are packaged. Addy's upstream README notes that individual skill installs can omit shared repository references; selected-skill packaging must include the required references without activating the entire lifecycle pack.
- **Permissions and isolation:** document filesystem, network, subprocess, and secret access. Start with no production credentials and bounded disposable fixtures. Keep account runtime homes isolated; distribute only explicitly allowed static assets. Never infer permission to install hooks from permission to load Markdown.
- **Compatibility:** test the actual supported Claude and Codex versions, discovery and invocation, provider build differences, hook trust requirements, fresh sessions, resume, account rotation, and remote runners. Unsupported combinations remain visibly unsupported. Experimental vendor surfaces retain constitution-required approval, pin, probe, kill switch, and fail-closed behavior.
- **Policy fit:** record overlaps and conflicts with the constitution, Portable Agent Contract, review policy, test commands, artifact layout, and completion workflow. Select one owner for each concern. Remove conflicting entry points from the approved selection or document a tested adapter; a generic instruction to ignore conflicts is insufficient.
- **Measured value:** run the candidate evals below against a baseline using the same tasks, engine/model versions, and budgets. Record correctness, false positives, unnecessary changes, reviewer usefulness, elapsed time, and token cost.
- **Approval and maintenance:** name an accountable maintainer and an approver distinct from the admission author. Store the approved hashes, eval report, compatibility matrix, review date, and rollback target. A changed hash, executable, permission, or reference reopens vetting. No automatic upstream updates enter the standard channel.

Admission states are proposed as `candidate → sandbox → pilot → approved`, with `rejected` and `revoked` exits. Availability and enforcement are separate: an approved skill may still be advisory for a particular project. Revocation prevents new managed execution; pending gates stay blocked or require an explicit, audited replacement or exception. It must never silently turn a missing check into a pass.

Extend the Portable Agent Contract with a reference to a versioned framework selection and lock manifest; do not maintain another independent list of installed skills. The manifest records upstream SHA, selected files and hashes, provider projection hashes, approved executable dependencies, compatibility, owner, and admission evidence. Generated instructions and the Library view derive from this source. Policy changes must be evaluated using the trusted base policy, so a PR cannot remove its own obligations by editing the manifest.

## 3. Three tiers

| Tier | What is enforced | Evidence and failure behavior |
|---|---|---|
| Deterministic checks | Reproducible policy and engineering assertions: approved hashes, complete projections, typed schemas, tests, lint, accessibility assertions, and agreed performance budgets. | Trusted runner records the command/check identity, input revision, tool version, outcome, and artifact digest. Failure or missing required evidence blocks the applicable transition. |
| Required review evidence | A scoped design, architecture, security, or process review occurred and its findings received a disposition. | Record reviewer identity, scope, source revision, framework/policy digest, findings, and resolutions or authorized exceptions. An author saying “reviewed” does not satisfy independent review. Missing or stale evidence blocks; subjective recommendations do not automatically become blockers. |
| Advisory judgment | Design taste, alternate architectures, optional simplification, and speculative optimization. | Findings are visible suggestions. They become requirements only through an explicit project decision, not an LLM score or keyword in a transcript. |

Applicability is resolved from the project profile, task requirements, changed paths, and declared interfaces. Paths are a conservative signal: backend changes can affect a UI contract. Agents may propose additional applicability, but cannot waive a mandatory obligation. Unknown applicability in an enforced profile requires triage, not an automatic skip. Documentation-only changes should not trigger browser or security tooling without a relevant change.

Gate integration adds evidence prerequisites to the existing design/spec, plan/build-handoff, and completion/review transitions represented by `server/sdlc/gates.py` and consumed by `server/sdlc/engine.py`. These are integration points, not claims that framework-specific gate identifiers already exist. Reuse the registry's risk and tolerance semantics; automatic resolution may occur only after required evidence passes. Existing high-risk human gates and release separation of duties remain authoritative.

Evidence must bind to repository identity, base/head revisions or immutable stage artifact, policy digest, framework digest, engine/model where relevant, run identity, and producer identity. New changes invalidate affected evidence; initially invalidate conservatively on any head change. Validate evidence server-side and authenticate its producer. Agent-written JSON and screenshots are supporting artifacts, not trusted check attestations. Keep sensitive artifacts access-controlled and redact credentials and user data.

Enforcement must cover direct/manual sessions as well as automated initiative sessions. Local hooks provide early feedback; a required repository CI check is the merge boundary. Report a project as only partially enforced if branch protection or the required check cannot be configured. Repository administrators can still bypass platform controls; retain an audit trail rather than claiming universal prevention.

Exceptions require an authorized owner, reason, scope, expiry, and compensating evidence. No self-issued exception may waive security or governance invariants. A framework kill switch stops its execution without disabling unrelated quality gates; affected work uses an approved fallback or remains visibly blocked.

## 5. Cross-project rollout

1. **Inventory and baseline.** Inventory existing project contracts, skills, frameworks, CI gates, and engine versions. Preserve incumbent instructions and design systems. Record a baseline corpus and cost/quality measurements before changing agent behavior.
2. **ViberPit Impeccable pilot.** Introduce the manifest, complete vetting of the installed selection, and run in observation mode. Initially require evidence presence and deterministic accessibility checks only after measuring false positives; keep aesthetic critique advisory.
3. **Portable adoption pilot.** Open opt-in adoption PRs for at least one other React project and one backend-only project. Use the existing `.agents/contract.json` / `.agents/agentctl.py` contract and pin the shared validator/workflow revision. The backend profile proves UI tooling is not activated unnecessarily. Include at least one project without the contract to prove non-destructive onboarding.
4. **Domain admissions.** Evaluate Superpowers compatibility and each Addy, Vercel, and Trail of Bits selection separately. Promote only the tested subset for applicable profiles. Keep Compound Engineering isolated until a comparison establishes a reason to adopt or replace existing behavior.
5. **Standard channel.** New managed projects receive a proposed base profile and stack/risk overlays through onboarding PRs. Existing projects migrate through reviewable diffs. Central releases propagate as upgrade PRs, not live global file replacement. Projects keep pinned effective policy; approved local additions may strengthen it, while weakening mandatory requirements needs a recorded exception.

Use `observe → evidence-required → enforced` per project and obligation. Show effective versions, applicability reasons, missing/stale evidence, exceptions, and rollback state through existing Library/SDLC surfaces. Session launch snapshots the effective policy and checks installed hashes; resume or host transfer must preserve or explicitly reconcile that snapshot. Never silently mix versions within an initiative's evidence chain.

Proposed promotion criteria: all deterministic and critical abuse tests pass; no critical safety failures; all required engine/host smoke tests pass; at least 20 representative behavioral tasks per candidate, repeated three times per supported engine/model configuration; domain acceptance at least 90%; no regression on mandatory baseline cases; false blocking at most 5% on clean cases. Report counts and uncertainty, not just percentages. Review median/p95 time and token cost against a budget fixed before the pilot (initial proposal: no more than 25% median overhead for routine tasks). These are proposed thresholds for ratification, not measured results. Human assessors use a fixed rubric for design and architecture usefulness; assessors should not know which framework produced a result where practical.

Roll back via a reviewed lock/profile change to the last approved revision. Preserve historical evidence and invalidate only evidence that no longer satisfies the effective policy. Security revocation takes effect immediately for new execution and pending acceptance checks, even for pinned sessions. Retire duplicate local copies and replaced instructions in the same adoption change. Each upgrade reruns integrity, conflict, behavior, and live compatibility tests appropriate to its changed scope.

Constitution check: I—supported engine surfaces only; II—isolated runtime homes and allowlisted static distribution; III—real engine/runner smoke evidence; IV—authenticated admission, least privilege, secret-safe artifacts; V—TDD and required quality gates for implementation; VI—extend the contract, gate registry, and eval harness; VII—versioned dependency and license vetting. No constitutional amendment is proposed here.
