## 1. Problem & Goal

The AI-Native SDLC Playbook describes a six-stage loop — **Plan → Design → Build → Test →
Deploy → Maintain** — whose core thesis is *"every stage commits an artifact the next stage
reads,"* with detection deterministic and judgment gated. ccswitch is a multi-account Claude
session orchestrator that **already implements the middle of this loop** (Build/Test/Review/
Deploy) via `backlog_runner`, `pr_doctor`, `cicd_doctor`, `pipeline`/`merge_train`, and
`autopilot`.

**Goal:** make ccswitch a first-class SDLC-orchestration engine by adding the two missing ends
of the loop — the **front** (intent → spec → plan artifact chain) and the **back** (a closed
control-band monitoring loop that re-enters the chain autonomously) — plus the **governance
control plane** (permission tiers, approval-gate hooks, CI evals) the playbook insists must
precede autonomy. The engine is dogfooded on ccswitch's own repository.

**Non-goals (v1):**
- Reinventing Build/Test/Deploy — those hand off to existing automations.
- Full autonomy. v1 is **propose-only**: every stage transition is generated by Claude but
  advanced by a human tap (mirroring `backlog_runner`'s `propose` mode).
- Multi-tenant / arbitrary-repo productization beyond what already works; the target-repo set is
  the existing `gitrepos` scope.

## 2. Decisions (locked)

| Decision | Choice | Rationale |
|---|---|---|
| Core scope | ccswitch **is** the SDLC engine (a product feature), not just repo hygiene | User directive |
| Artifact source of truth | **Committed in the target repo** (`docs/sdlc/<slug>/*.md`); DB holds an index with the git SHA per artifact | Playbook Option 1; "git is the master audit trail" |
| Autonomy (v1) | **Propose-only**, human gate at every stage | Prove the chain before trusting autonomy; evals/governance land in Phase 3 |
| First milestone | **Artifact-chain spine + front stages** (Phase 1) | `intent.md` is the shared currency every other stage reads/writes |

## 3. Architecture

### 3.1 The Initiative and its artifact chain

One new first-class object threads the loop:

- **`Initiative`** — a unit of SDLC work with a `slug`, `repo`, current `stage`, `status`, and
  an ordered chain of artifacts.
- **`InitiativeArtifact`** — one committed markdown artifact in the chain
  (`kind ∈ {intent, spec, plan}`), recording the **repo-relative path**, the **git commit SHA**
  that is authoritative, the PR that produced it, and generation metadata (session id, model).

```
intent.md ──▶ spec.md ──▶ plan.md ──▶ code diff (PR) ──▶ review ──▶ deploy ──▶ incident
  (Plan)      (Design)     (Build)      (Build)         (Deploy)   (Deploy)  (Maintain)
                                          └── EXISTING backlog_runner + pr_doctor ──┘
                                                                          │
                     new intent.md ◀── control-band monitor (Phase 2) ◀───┘   (loop closes)
```

**Source of truth = the target git repo.** Each artifact is committed at
`docs/sdlc/<initiative-slug>/<kind>.md`. The DB row stores the SHA and path; the DB is an index
and state-machine, never the authority. Reading an artifact = reading the file at that SHA.

### 3.2 Everything new follows the existing automation mold

The exploration confirmed a uniform substrate: every automation implements the `Automation`
Protocol (`server/automations/base.py`) and runs a fully-injected `tick()` control loop with
durable `AutomationTargetState` and an `AutomationEvent` activity feed
(`server/automations/context.py`). **New SDLC stages are new automations in this exact mold —
not a parallel engine** (constitution VI: single source of truth / no dead code).

| New component | Shape | Reuses |
|---|---|---|
| `Initiative`, `InitiativeArtifact` models | DB spine + git-SHA index | `server/db/models.py` conventions (UUID PK, UTC ts, JSON cols, nullable-add reconcile) |
| `server/sdlc/engine.py` | **Pure** stage-decision fns `advance(initiative, artifacts) → StageAction` | mirrors `pr_doctor_engine.py` purity + `plan_recovery()` shape |
| `server/sdlc/prompts.py` | Pure seed-prompt builders per stage | mirrors `backlog_prompt.build_implement_prompt()` |
| **Intake** automation | Triage item → committed `intent.md` PR | `Automation` Protocol, `AutomationContext.spawn_session` |
| **Synthesizer** automation | `intent.md`→`spec.md` (org skills as constraints); `spec.md`→`plan.md` (plan mode) | headless `spawn_session`/`ccrun`, `AutomationContext` |
| **Control-band monitor** (Phase 2) | Deterministic detection over ccswitch metrics; breach → headless diagnosis → `intent.md` | `bands.yaml`, `server/obs/`, `server/pipeline/` |
| Org **skills/hooks/REVIEW.md** (Phase 3/4) | Version-controlled policy in `.claude/` | new `.claude/` tree |
| **Eval suite** in CI (Phase 3) | Regression tests for agent-config changes | `.github/workflows/ci.yml` |
| `/api/sdlc/*` + Initiative board | REST + web view of the chain and triage queue | `server/api/` router pattern, `web/src/` React Query + WS |

### 3.3 Stage engine (pure core, injected I/O)

Following the `pr_doctor_engine` / `backlog_runner` pattern, all decision logic is pure and
testable; all I/O is injected:

```python
# server/sdlc/engine.py  (pure — no I/O, 100% unit-testable)
def next_action(initiative, artifacts, mode, config) -> StageAction:
    # StageAction ∈ {Propose(kind), AwaitApproval(kind), HandoffToBuild(issue), Done, NeedsHuman}
    ...
```

The **Intake** and **Synthesizer** loops inject: `read_initiatives()`, `spawn(prompt, repo)`,
`commit_artifact()`, `open_pr()`, `read_config()`, `clock()` — mirroring `BacklogRunnerLoop`'s
seams so tests use fakes and prod wires the orchestrator.

### 3.4 Stage-transition jobs are non-interactive Claude sessions

Each transition is a spawned session (`AutomationContext.spawn_session`, deduped by
`origin_ref = initiative-slug:kind`), seeded with the upstream artifact and — for spec — the
org skills as constraints. Output is a committed PR (`docs/sdlc/<slug>/<kind>.md`), never a
draft. **v1 propose-only:** the loop stops after opening the PR and emits a `proposed` event; a
human tap (or auto-merge of that PR) advances the Initiative to the next stage.

### 3.5 Build/Deploy reuse, not reinvention

Once `plan.md` is approved, the Initiative's Build stage **hands the underlying GitHub issue to
the existing `backlog_runner`** (which already does issue→session→PR) and `pr_doctor` carries
the PR through CI. Deploy reuses `pipeline`/`merge_train`. The Initiative object simply *tracks*
these existing flows by correlating on `origin_ref`; it does not duplicate them.

## 4. Data flow (the closed loop)

1. **Trigger** — a human brainstorm session *or* (Phase 2) a control-band breach files a triage
   item.
2. **Intake** → commits `intent.md` (git author + timestamp = audit trail). *Human gate.*
3. **Synthesizer** → `spec.md` PR with org-policy concerns flagged; human resolves. *Human gate.*
4. **Synthesizer (plan mode)** → `plan.md` PR naming files/order/tests. *Human gate.*
5. **Build** → hands issue to `backlog_runner`; `pr_doctor` + CI carry it.
6. **Deploy** → existing `pipeline`/`merge_train`; a **prod-gate hook** (Phase 3) requires named
   authorization — the agent that wrote the change cannot authorize its release (separation of
   duties).
7. **Maintain** (Phase 2) → control-band monitor watches post-deploy metrics; a breach re-enters
   at step 1 as a new `intent.md`. **Loop closed.**

## 5. Persistence

New models in `server/db/models.py` (following conventions: `String` UUID PK, UTC `DateTime`,
JSON cols, **nullable-added** so `_reconcile_columns` picks them up on SQLite + Postgres). Adding
models means updating the two hand-maintained lists in `server/tests/` (`_REQUIRED_EXTRAS`,
`RECONCILE_EXEMPT`) and re-running the Postgres compat suite, plus an Alembic revision chained off
the newest `down_revision` (reviewable record; reconcile applies it).

```
Initiative
  id (uuid pk) · slug (unique) · repo · title · stage (enum: intake|design|plan|build|deploy|maintain|done)
  status (enum: proposed|active|awaiting_human|blocked|done) · origin (e.g. "human"|"control-band")
  origin_ref (nullable) · created_at · updated_at

InitiativeArtifact
  id (uuid pk) · initiative_id (fk, index) · kind (enum: intent|spec|plan)
  repo_path · commit_sha (nullable until merged) · pr_number (nullable) · pr_url (nullable)
  session_id (nullable) · model (nullable) · created_at
```

State-machine counters (attempts, proposed-flag, backoff) live in the existing
`AutomationTargetState` keyed by initiative slug — no new state table, matching `backlog_runner`.

## 6. API & Frontend

- **`server/api/sdlc.py`** — `APIRouter(prefix="/api/sdlc")`, all routes `Depends(current_identity)`:
  `GET /initiatives`, `POST /initiatives` (from a session or triage item), `GET /initiatives/{slug}`
  (chain + artifact SHAs), `POST /initiatives/{slug}/advance` (the human-gate tap),
  `GET /triage` (Phase 2 queue). Registered in `server/app.py`.
- **Web** — an **Initiative board** (`web/src/`) rendering the artifact chain as a horizontal
  track (reusing the `PipelineView`/`MetroTrack` idiom), each artifact linking to its committed
  file at its SHA, with an "Advance" button per gate. React Query hooks mirror `useDashboard`;
  live updates over the existing `/ws`.

## 7. Governance & Evals (Phase 3)

- **Permission tiers by environment** reuse ccswitch's existing `permission_mode` resolution:
  dev = `full-auto`, staging = mid, prod = gated.
- **Approval-gate hooks** in `.claude/settings.json` block prod deploy unless `RELEASE_APPROVAL`
  is set; managed (non-overridable) hooks own the non-negotiables (constitution IV).
- **CI eval suite**: 20–50 real recent ccswitch tasks with acceptance checks, run on any change to
  `CLAUDE.md`/skills/hooks; a pass-rate threshold gates the merge. Each production incident adds a
  regression eval.

---

## 8. Testing strategy (constitution V — TDD + quality gates)

- **Pure engine** (`server/sdlc/engine.py`, `prompts.py`): exhaustive unit tests with no I/O, the
  way `pr_doctor_engine` is tested.
- **Loops**: fakes for every injected seam (spawn, commit, PR, config, clock) — deterministic,
  no network/DB — matching `BacklogRunnerLoop` tests.
- **API**: `server/tests/` with pinned `CCSWITCH_TAILNET_ALLOWLIST` per test.
- **Gate before push (all four):** `ruff check src/ server/`, `mypy server/ --ignore-missing-imports`,
  `pytest tests/`, `pytest server/tests/`; web: `vitest run`, `tsc --noEmit`, `eslint`.
- New models → re-run Postgres suite (`CCSWITCH_TEST_PG_URL`) + update the two schema lists.

## 9. Phasing (implementation order)

- **Phase 1 — Spine + Front Stages (this spec's build target):** `Initiative`/`InitiativeArtifact`
  models + migration, `server/sdlc/` pure engine + prompts, **Intake** + **Synthesizer**
  automations (intent→spec→plan, propose-only), `/api/sdlc` + Initiative board, Build handoff to
  `backlog_runner`. Ships a complete, demoable vertical slice on ccswitch's own repo.
- **Phase 2 — Maintain loop:** `bands.yaml` control-band monitor over ccswitch metrics
  (`obs`/`pipeline`), Western-Electric-style deterministic detection, headless diagnosis →
  `intent.md` into the triage queue. Closes the loop.
- **Phase 3 — Governance & Evals:** permission tiers, approval-gate hooks (incl. managed
  settings), CI eval suite gating agent-config changes.
- **Phase 4 — Review polish:** `REVIEW.md` review policy wired into `pr_doctor` / `/code-review`;
  `@claude`-style comment-driven fixes on Initiative PRs.

## 10. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Parallel implementation of an existing flow (e.g. re-doing backlog Build) | Initiative *correlates* on `origin_ref`; Build/Deploy strictly hand off. Enforced in review (constitution VI). |
| DB/repo drift (index vs. committed truth) | Repo SHA is authoritative; DB stores SHA only; a reconcile reads the file at SHA on display. |
| Spec/plan generated for unwanted work | Propose-only v1: every stage needs a human tap; measure `intent.md` survival rate. |
| Schema-drift startup failure from new models | Add columns nullable; update `_REQUIRED_EXTRAS`/`RECONCILE_EXEMPT`; Alembic revision; run PG suite. |
| Autonomy before controls exist | Governance/evals (Phase 3) gate any move past propose-only. |

---

## 11. Success measures (from the playbook)

- **Leading:** time from brainstorm → committed `intent.md`; elapsed `intent.md`→`spec.md`;
  share of Initiative PRs merging first-pass.
- **Lagging:** `intent.md` survival rate to next stage; requirements rework after Build starts;
  (Phase 2) time from band breach to triage queue; share of findings that become merged fixes.
