# Spike D — `claude setup-token` as the headless-auth primitive

**Date:** 2026-06-28
**Question:** Can a per-account `claude setup-token` replace the OAuth-grant-harvest + refresh
(+ passkey) scheme — i.e. is it long-lived, SDK-consumable, and concurrency-safe?
**Verdict:** ✅ PASS on all four — strong candidate to REPLACE the passkey/Phase-3 approach.

## Results (binary: Claude Code 2.1.195, real Max account `primary`)

| Question | Result |
|---|---|
| **Lifetime** | Token explicitly **"valid for 1 year"**. Opaque bearer `sk-ant-oat01-…` (not a rotating JWT). |
| **SDK/CLI consumption** | `CLAUDE_CODE_OAUTH_TOKEN=<tok>` in a **creds-less** `CLAUDE_CONFIG_DIR` → `claude -p` authenticated and answered. No stored `.credentials.json` needed. Fits ccswitch's per-process env model. |
| **Concurrency** | **6 parallel** `claude -p` calls sharing the same token → all exit 0, no 401, no rotation error. |
| **Rotation/consumption** | Token **still valid after** concurrent use. Stable bearer — does NOT rotate per use. |

## Why this matters

- The current in-session 401 churn stems from **single-use refresh-token rotation** (e.g. the
  kindash self-collision). A `setup-token` is a **stable, non-rotating** bearer, so that entire
  failure class disappears.
- Re-auth cadence drops from ~daily to **~annual** (1-year token), regenerated by one interactive
  `setup-token` run (manual code-paste OAuth; no loopback/callback port needed — friendly to a
  headless host).

## Proposed architecture (replaces Phase 3 passkey pipeline)

1. Per account, run `claude setup-token` once (interactive, ~yearly).
2. Store the token in the **GNOME keyring** via the existing `crypto.py` / `secret-tool` path
   (same pattern as the master key) — no new secrets subsystem.
3. ccswitch sets `CLAUDE_CODE_OAUTH_TOKEN` per session process (per-process isolation preserved).
4. Drop: the grant-harvest/refresh churn, the passkey/virtual-authenticator pipeline, the `op`
   password fallback. Keep: Phase 1's in-session-401 hardening (still useful), audit instrumentation.

## Caveats / follow-ups

- **Token generation is interactive** (code-paste OAuth) — still needs a human ~yearly. Acceptable.
- **Revocation path** not yet mapped — confirm how to revoke/rotate a leaked or stale `oat` token
  (account settings vs. regenerate). NEEDED before relying on it.
- **ToS/quota** — `setup-token` is the sanctioned subscription-headless mechanism, but confirm
  multi-session quota behavior matches today's `claude` usage.
- The Spike A/B passkey findings remain a documented *fallback* if `setup-token` is ever withdrawn.

## SECURITY NOTE (this spike)

During the spike, the generated `primary` token (scope `user:inference`, 1-yr) was accidentally
printed into the session transcript by a log-grep. It was wiped from disk; it MUST be revoked —
its blast radius is inference calls against `primary`'s Max quota (no account/data access).
